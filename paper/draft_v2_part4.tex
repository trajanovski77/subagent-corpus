\section{Discussion and Implications}
\label{sec:discussion}

\subsection{Withholding permission is not withholding authority}
\label{sec:disc-leastpriv}

Specifications meant to inspect are given file-writing tools far less often than those meant to change code, and the
gap survives every curation cut and is paired within repositories. Whether written or copied, these grants withhold
\code{Write} from reviewers: least privilege is being applied in a setting where nothing compels it. Once the shell is
counted, however, the gap shrinks from \RQtwoRoleGapWrite{} to \RQtwoRoleGapAuthority{} (\S\ref{sec:res-rq2}), so most
of the difference concerns which tool names appear in a list, not what the delegate can reach. The withholding applies
to permissions, and a tool allowlist enumerates permissions,
not authority. Because a shell carries the process's ambient file-system authority \citep{miller2003capability},
removing the file-writing tools $W=\{\code{Write},\code{Edit},\code{NotebookEdit}\}$ from a grant $T$ that retains an
unsandboxed \code{Bash} leaves its authority over files unchanged, $A(T \setminus W) = A(T)$, in the execution contexts
of \S\ref{sec:capmodel}. In that context the grant $\{\code{Read}, \code{Grep}, \code{Glob}, \code{Bash}\}$, which reads like a reviewer's,
gives the same access to files as a read--write grant; in \code{default} mode only the user's approval of each command
keeps the two apart.

A retained shell is not always a mistake. Some write-withholding specifications ask for builds and tests, and a
minority ask for state-changing commands, but most need at most read-only commands or none (\S\ref{sec:res-rq3}). For
those, the shell adds authority the text never asks for; for the rest, the problem is that the tool list offers no way
to grant part of a shell's reach. The same limitation leaves the residual inspect--change gap without a normative
baseline: codebook R counts a delegate that runs tests or analyses and only reports as inspection, so some inspect-mode
delegates need a shell, and the tool vocabulary has no partial shell to grant them. For delegates whose text asks only
to read, a shell limited to read-only commands would provide what the text asks for, but a command pattern in the
\code{tools} field did not provide that limit in our probe (\S\ref{sec:res-rq3}). The documented mechanism is a Bash
deny rule in settings, which applies to subagents \citep{AnthropicSubagentsDoc}, and such rules match command text: the
documentation's own example shows a \code{git log} rule matching \code{git log --output=<file>}, which writes a file
\citep{AnthropicPermissionsDoc}. Verification is a genuine need, and test runners execute repository code and write
caches and build outputs, so a verify-type shell needs a sandbox or a writable scratch directory rather than a command
pattern.

\paragraph{Existing access controls do not carry over.}
Repositories that protect their default branch have slightly more dominated withholding, not less
(\S\ref{sec:res-rq7}), and settings that deny writes or shells and scoped CI tokens show no clear difference. The
outcome counts all specifications, so it also rises with how often a repository withholds file tools at all, and the
evidence is observational, with many uncontrolled differences between repositories; the small positive difference
should not be read as an effect. It does show that conventional access-control discipline does not go with fewer
dominated withholdings.

\paragraph{Why the abstraction invites the error.}
Four features of the \code{tools} field make the error easy to make. First, it puts objects at different levels in one
list. Lampson's access matrix treats each object as an independent column whose rights are granted separately
\citep{lampson1974protection}, but the field mixes resource operations (\code{Read}, \code{Write}, \code{Edit}) with an
interpreter (\code{Bash}) that can perform any of them. Second, it guards the direct path and not the indirect one.
Tools tend to protect the obvious interface and miss indirect routes to the same resource
\citep[\S4.2]{garfinkel2003traps}, and file-editing deny rules do not cover subprocesses that write files indirectly
\citep{AnthropicPermissionsDoc}. Third, its default is the opposite of fail-safe: omitting \code{tools} grants
everything, so the least deliberate configuration is the most privileged one, contrary to basing access on permission
rather than exclusion \citep{saltzer1975protection}, and \RQtwoImplicitEng{} of specifications omit the field.
Fourth, the resolver pushes delegates towards the shell. It removes \code{Grep} and \code{Glob} whenever \code{Bash}
resolves, for no documented reason we know of, so routine search moves onto the shell, while \code{Write} and
\code{Edit} stay in place without a warning.

\subsection{An agent-configuration security smell}
\label{sec:disc-smell}

Coarse settings that defeat finer controls beside them recur in configuration security (\S\ref{sec:rw-smells});
Table~\ref{tab:smells} places our pattern in that family. We name \textbf{unscoped shell in a restricted role} as a candidate security smell: a
specification that withholds file-writing tools while granting a shell without a command scope. It maps to CWE-250
(execution with unnecessary privileges) and to CWE-653 (improper isolation or compartmentalisation), because the file
tools were separated from the grant while one tool that spans them was not \citep{cwe250,cwe653}. It matters only
where shell commands run without per-command approval and without a sandbox (\S\ref{sec:capmodel}). The linter
released with this paper reports the specification-level pattern; it does not consult permission modes, settings or
hooks, and neither the smell nor the linter's precision has been validated with practitioners.

\subsection{Prompt restrictions and enforced grants}
\label{sec:disc-prompts}

That an agent with a shell can write when asked, with commands approved automatically, is expected, and the
mechanism check confirms it. What happened when the prompt forbade the change is more useful for practice. In the
realistic inspection configuration the prompt restriction worked for Sonnet and Opus and left Haiku completing \ExpCthreeHaiku{} of the changes it
forbids. The restriction was one explicit wording, stronger than most real restrictions, against direct requests, so
these rates are a best case for prompts and say nothing about adaptive attacks. A restriction that holds or fails with
the model is a property of the model, not of the configuration, and \RQfiveNoModelPooled{} of specifications (pooled;
repository mean \RQfiveNoModel{}) do not name the model that will read them. The two channels also fail differently: a
missing tool produces an error the parent can see, an unheeded prompt a completed change, and Haiku's false claims
show that the delegate's report is not a reliable record either. Finally, on one fixture with explicitly report-only
tasks, no agent changed files under any grant. This bounds the per-configuration rate of unrequested changes only for benign,
explicitly report-only tasks (one small fixture, two tasks, \nOverRepsFinal{} repetitions per cell, no adversarial
content), not for ambiguous requests such as ``fix if needed'', longer sessions or prompt injection. It agrees with
\citet{qu2026overeager}, who observe no over-eager actions by Claude Code when the prompt declares the authorised scope
and 17.1\% when that declaration is removed from scenarios built to invite such actions; our tasks state their scope
(``tell me''). For such tasks, the risk of a dominated withholding lies less in delegates acting
unasked than in a grant that does not refuse a change when one is requested. Our requests came from the parent;
whether content the delegate reads can produce such a request \citep{debenedetti2024agentdojo} we did not test. The
enforcement-channel fields of a specification (\code{tools}, \code{disallowedTools}, \code{permissionMode},
\code{hooks}, \code{isolation}) are the only ones that do not depend on the model agreeing, and a prompt restriction
that holds for some models is not a security control. Nor does either channel contain a delegate's side effects: the
runs that wrote outside their fixture directory, by running a script from the wrong directory or by ``deleting'' a file
into the user's Trash (\S\ref{sec:res-rq5}), were prevented neither by the grant nor by the prompt; only a sandbox
confining writes to the fixture could have.

Two trust boundaries lie outside our measurements. A delegate's answer returns to a parent that usually holds more
authority, so restricting the delegate does not stop content it reads from reaching the parent; Haiku's false
completion claims are a benign case of a parent receiving unreliable output. And a delegate that can write files, by
a tool or through a shell, can edit agent specifications, settings or git hooks and so widen grants in later
sessions.

\citet{Yan2026DoNotDeny} found that few security rules in context files have an enforced counterpart; we find the
same gap inside one artifact: when a specification's text makes the agent read-only, its grant can usually still reach
the file system (\RQfourFullReaches{}). The restriction is stated in the interpretive channel and only partly carried
into the enforced one.

\subsection{Specifications as maintained artifacts}
\label{sec:disc-drift}

Most files naming a removed tool were committed after the removal (\S\ref{sec:res-rq6}), so they were already
unresolvable on current builds when committed rather than overtaken by the runtime later; users of older builds may
still resolve them. Because most of the corpus was itself committed after these removals, the share dates the
staleness, not its source. This places the staleness at authoring time, which is consistent with the reuse we measure
(\S\ref{sec:res-rq1}) and with copy-based reuse of skills and editor rules
\citep{Destefanis2026GitSkills,Jiang2026CursorRules}. The feedback is asymmetric: the settings layer warns about a deny
rule that matches no tool, while the subagent resolver says nothing about a dropped name, a collision or a file it
does not load. Periodic revalidation would not prevent it, since the names are already stale when written; a resolver that
reports what it dropped would.

\subsection{Implications}
\label{sec:disc-implications}

\paragraph{For practitioners.} Omitting \code{tools} grants everything. An agent that holds an unscoped shell is not
read-only, whatever its prompt says, unless each shell command needs approval or runs in a sandbox. Where the text asks
only to read, restrict the shell with Bash deny rules in settings, which can be bypassed \citep{Chen2026Denylist}, not
with a command pattern in the \code{tools} field; where the restriction must hold, or the text asks to build or test,
use a sandbox (\S\ref{sec:disc-leastpriv}). Do not treat a prompt restriction as a security control; if one matters, pin the model and
test it. Check that tool names resolve on the release you run and that every \code{name} in an agent directory is
unique. The linter released with this paper reports all of these and exits non-zero on dominated withholdings,
ignored files and duplicate names.

\paragraph{For tool builders.} The resolver should report what it drops (\S\ref{sec:disc-drift}) and warn on a
dominated withholding, which may not be what its author intended. Read-only should be a property of the execution
environment, enforced where every subprocess is covered, by a sandbox or a capability mode \citep{watson2010capsicum}.
Grants should be typed and attenuable: a shell grant should carry a file-system and network scope
\citep{moore2014shill}, and policies should inspect arguments rather than tool names \citep{shi2025progent}, outside
the model \citep{debenedetti2025defeating}. Where a narrow tool
can replace the shell, ship the narrow tool \citep{beurerkellner2025design}. The common principle is to separate the
interpreter from the resource operations: file-system, network and process authority should be properties of the
execution environment a delegate runs in, not names in a list that sits beside an interpreter able to exercise them
all.

\paragraph{For researchers.} The effective configuration should be measured by executing its consumer. Resolution
depends on the build (\nRemovedNames{} names that earlier releases accepted no longer resolve), and parsing the files
would have missed the dropped search tools, the silently discarded names and the shadowed files; pin the build and
release the oracle with the data. Permission and authority should be reported separately, as should explicit
grants and inheritance, since the measures lead to different conclusions (\S\ref{sec:res-rq2}). Behavioural claims
need repeated execution, reported per model and including tasks that do not ask for the behaviour: a single run shows
what is possible, not how often it happens, and prompt compliance differed by model. Intent needs validating as a
construct rather than trusting as a label: agreement between model raters was lowest on the intended mode, the construct
least privilege is judged against, so studies of over-privilege need human-validated intent. The corpus and oracles are released for longitudinal replication.
